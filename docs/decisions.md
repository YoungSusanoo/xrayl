# Архитектурные решения

[README](../README.md) · [Текущая архитектура](architecture.md)

Здесь отделены реализованные решения от вариантов на будущее. Поведение
команд описано в [commands.md](commands.md), детали хранения — в
[database.md](database.md).

## Логика хранения в PostgreSQL — принято

Нормализация, поиск существующих записей и атомарное создание выполняются
SQL-функциями. Уникальные индексы и составные внешние ключи защищают данные
независимо от пользовательского диалога. Go-хранилище вызывает функции
и преобразует результаты в типы приложения.

Это сохраняет правила записи в одном месте. Изменения этих правил требуют
миграций и проверки на PostgreSQL; Go-тесты flow отдельно проверяют сценарии.

## Сохранение значения до контекста — принято

Выбор определения сразу сохраняет значение и обновляет синонимы. Контекст
необязателен и создаётся отдельной операцией. Отмена ввода контекста или
отсутствие источников оставляет значение в словаре.

Это позволяет быстро добавить слово без контекста. До успешной записи
контекста смена команды или перезапуск завершает его ввод; уже сохранённое
значение остаётся.
Бот явно сообщает об этой границе сохранения.

## Независимые flow и отдельное создание источника — принято

Диспетчер хранит один flow на `(chatID, userID)`. `Addword`, `Words`,
`Addsource` и `Sources` принимают внутреннее сообщение и возвращают тексты ответов
с признаком завершения `Result.Done`. Внутри `Addword` выбор источника и ввод контекста — обычные
состояния, выбираемые через `switch`.

Источник создаётся отдельной командой `/addsource`, а при добавлении слова
выбирается из существующих. Запуск новой основной команды заменяет диалог
без автоматического возврата. Это ограничивает сложность управления
состояниями и отменой.

## Контекст одним текстовым полем — принято

После выбора источника пользователь отправляет одно сообщение. Оно сразу
сохраняется в `quote`; глава, страница или таймкод при необходимости входят
в тот же текст в формате пользователя. Отдельного поля и шага места нет.
Это сокращает диалог и не требует разбирать содержимое контекста.

Миграция `0006` переносит старое место в текст, сохраняя сведения. Откат
восстанавливает структуру БД, но не разделяет объединённый текст обратно.

## Единая маршрутизация сообщений — принято

В приложении зарегистрирован один обработчик Telegram-адаптера.
Он проверяет обновление, извлекает команду и передаёт внутреннее сообщение
диспетчеру. Таблица фабрик внутри диспетчера выбирает сценарий;
сам сценарий не знает о Telegram SDK или доставке ответа.
Распознавание команд сохраняет прежние правила Telegram entity.

## Последовательная очередь на сессию — принято

Входной обработчик Telegram работает синхронно с одним воркером и только
ставит сообщения в очереди. Каждая сессия имеет собственный обработчик,
который последовательно выполняет сценарий и отправляет его ответы.
Это сохраняет порядок внутри сессии и позволяет другим сессиям работать
во время ожидания словаря, БД или Telegram. Общая блокировка не охватывает I/O.

Очередь содержит до 32 ожидающих сообщений. Переполнение отклоняет новый
ввод; после обработки накопленного ввода отправляется одно уведомление
о пропусках. `/cancel` и смена команды следуют обычному порядку очереди.

Состояние фиксируется до отправки. Неоднозначная доставка не откатывает
переход и не повторяет запись. Автоматических повторов доставки нет.
Гарантия однократной записи при неоднозначной ошибке БД сюда не входит.

## Сессии в памяти с очисткой — принято

Сессии без активности удаляются через 30 минут при проверке раз в минуту.
Выполняющиеся операции и ожидающий ввод защищены от очистки.
Завершённый сценарий сразу освобождает свои данные. Перезапуск теряет
диалоги; совместное использование сессий несколькими экземплярами
приложения не поддерживается.

При остановке общий контекст отменяется, новый ввод отклоняется,
обработчики завершаются до закрытия БД. Необработанная очередь не сохраняется.

## Граница между API и личным словарём — принято

Определения запрашиваются через адаптер FreeDictionaryAPI.com.
Приложение сохраняет выбранное определение и его собственные синонимы;
метаданные API остаются в текущем ответе. Источники пользователя и контексты
хранятся отдельно от ссылок и сведений о лицензии словаря.

Просмотр личного словаря зависит только от PostgreSQL. Требование получать
все значения исключительно через внешний API не закреплено в БД:
SQL-функцию можно вызвать с собственным определением.

## Вложенные flow — отложено

Обсуждавшийся вариант:

```text
Addword
  └─ AddContext
       └─ AddSource
```

В нём `Addword` после записи значения передаёт сообщения `AddContext`.
Создание нового источника запускается дочерним `AddSource`, который после
завершения предоставляет результат через `Result()`. Один и тот же
`AddSource` используется самостоятельно и как вложенный шаг.

Обсуждавшееся правило отмены: родитель перехватывает `/cancel` до делегирования
и завершает весь активный сценарий с поддиалогами, сохраняя уже записанные
данные. Возврат на один шаг можно было бы выделить в отдельный `/back`.

Вариант отложен: передача результата, порядок обработки отмены и возврат
между диалогами добавляют сложность, пока для источников достаточно отдельной
команды. В коде нет дочерних flow, метода `Result()` или команды `/back`.
Вернуться к этому решению стоит, если предварительное создание источников
будет регулярно мешать добавлению слов.
