# Запуск и проверки

[README](../README.md) · [Команды бота](commands.md) · [База данных](database.md)

## Требования

- Go версии из [go.mod](../go.mod): сейчас `1.27.0`.
- Docker с Docker Compose для локальной PostgreSQL.
- Токен Telegram-бота и доступ к Telegram API и FreeDictionaryAPI.com.

Приложение запускается как Go-процесс. Compose поднимает только PostgreSQL;
используемый образ зафиксирован в [compose.yaml](../compose.yaml).

Все команды ниже выполняются из корня проекта.

## Настройка окружения

Создайте локальную конфигурацию:

```sh
cp .env.example .env
```

Заполните переменные по образцу [.env.example](../.env.example):

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | Токен Telegram, обязателен для бота |
| `DATABASE_URL` | Строка подключения PostgreSQL, обязательна для бота и мигратора |
| `POSTGRES_USER` | Пользователь для начальной настройки контейнера; по умолчанию `xrayl` |
| `POSTGRES_DB` | База для начальной настройки контейнера; по умолчанию `xrayl` |
| `POSTGRES_PASSWORD` | Пароль контейнера, обязателен для основного Compose |
| `POSTGRES_PORT` | Порт PostgreSQL на хосте; по умолчанию `5432` |
| `POSTGRES_TEST_PORT` | Порт отдельной тестовой PostgreSQL; по умолчанию `55432` |

Бот и мигратор загружают `.env` через `godotenv.Load`. Уже установленные
переменные окружения имеют приоритет. Файл `.env` необязателен, если нужные
значения переданы через окружение; он исключён из Git.

`POSTGRES_*` настраивают контейнер, а приложение использует `DATABASE_URL`.
Логин, пароль, база и порт в строке подключения должны соответствовать
Compose. При изменении порта обновите и `DATABASE_URL`. Специальные символы
логина и пароля в URL нужно кодировать. Пароль `change_me` в примере следует
заменить своим значением в обоих местах.

## База, миграции и запуск

```sh
docker compose config --quiet
docker compose up -d --wait
docker compose ps
go run ./cmd/migrate status
go run ./cmd/migrate up
go run .
```

База публикуется только на `127.0.0.1`. Её данные находятся в volume
`postgres_data`, смонтированном в `/var/lib/postgresql`. Обычный
`docker compose down` сохраняет этот volume. После инициализации существующей
БД изменение `POSTGRES_USER`, `POSTGRES_DB` или `POSTGRES_PASSWORD` не меняет
созданные роли, базы и пароли автоматически.

Бот проверяет соединение с PostgreSQL с тайм-аутом пять секунд.
Миграции автоматически не применяются: запускайте `migrate up` перед ботом
после получения изменений схемы. Во время работы бот получает обновления
Telegram через long polling.

Для остановки бота используйте `Ctrl+C`, SIGINT или SIGTERM. Корневой контекст
отменяется, соединение с БД закрывается. Для остановки контейнера:

```sh
docker compose down
```

## Управление миграциями

Мигратор поддерживает ровно три команды:

```sh
go run ./cmd/migrate status
go run ./cmd/migrate up
go run ./cmd/migrate down
```

`status` показывает версии, состояния и пути миграций. `up` применяет все
ожидающие миграции; повторный запуск не меняет уже применённые версии.
`down` откатывает одну последнюю миграцию.

SQL-файлы из [каталога миграций](../internal/storage/postgres/migrations)
встраиваются в исполняемый файл. Goose записывает версии в таблицу
`goose_db_version`. Команды мигратора используют PostgreSQL advisory lock
для последовательного выполнения и ограничены одной минутой вместе с
подключением и ожиданием блокировки.

Откат `0001` удаляет таблицы и данные; откат `0003` удаляет синонимы.
Остальные последствия перечислены в [описании БД](database.md).
Сценарии отката проверяйте на отдельной тестовой базе.

При переходе на `0006` остановите бот, примените миграции и запустите
обновлённую версию: сигнатура записи и результат чтения контекста изменяются.
То же согласование версии приложения со схемой нужно при откате на `0005`.

## Обычные проверки

```sh
go test -race ./...
go vet ./...
go build ./...
```

Обычные тесты не требуют PostgreSQL, токена Telegram или внешнего API.
HTTP-взаимодействие проверяется локальными серверами и тестовыми транспортами.
`go build ./...` проверяет сборку пакетов; для запуска используйте `go run .`.

## Интеграционные проверки

Тестовый Compose-проект использует отдельную базу `xrayl_test` на порту
`55432` и хранит данные в памяти контейнера. Настройки находятся в
[compose.test.yaml](../compose.test.yaml); основной volume не затрагивается.

```sh
docker compose -p xrayl-migrations-test -f compose.test.yaml up -d --wait
TEST_DATABASE_URL='postgres://xrayl:xrayl_test@127.0.0.1:55432/xrayl_test?sslmode=disable' \
  go test -race -tags integration -count=1 ./...
docker compose -p xrayl-migrations-test -f compose.test.yaml down
```

После тестов выполните последнюю команду и при неуспешной проверке.
Удаление тестового контейнера удаляет его данные.

При занятом порту задайте `POSTGRES_TEST_PORT` в окружении команды Compose
и укажите такой же порт в `TEST_DATABASE_URL`. Тесты требуют явный
`TEST_DATABASE_URL`; `DATABASE_URL` бота вместо него не подставляется.
Каждый тест создаёт отдельную схему и удаляет собственную схему после работы.
Общая подготовка БД находится в [internal/testutil](../internal/testutil) и
доступна только при сборке с тегом `integration`. Имена схем генерируются
случайно, чтобы параллельно запускаемые тестовые пакеты не пересекались.

Проверки SQL-функций, хранилища и миграций остаются в
[internal/storage/postgres](../internal/storage/postgres). Сквозные сценарии
Telegram → диспетчер → словарь → PostgreSQL находятся отдельно в
[tests/integration](../tests/integration). Оба набора включаются общим тегом.
Для запуска только сквозных сценариев при работающей тестовой БД:

```sh
TEST_DATABASE_URL='postgres://xrayl:xrayl_test@127.0.0.1:55432/xrayl_test?sslmode=disable' \
  go test -race -tags integration -count=1 ./tests/integration
```

Проверяются миграции и откаты, ограничения схемы, атомарность и конкурентные
вызовы функций, нормализация синонимов, изоляция пользователей, отмена
контекстов и тайм-ауты. Сквозные сценарии используют настоящую PostgreSQL,
локальный API словаря и локальный Telegram API: добавление значения,
создание источника, сохранение контекста и просмотр словаря.

## Диагностика

| Ситуация | Что проверить |
| --- | --- |
| `BOT_TOKEN is not set` | Токен в `.env` или окружении процесса |
| `DATABASE_URL is not set` | Строку подключения и рабочий каталог при загрузке `.env` |
| Ошибка соединения с PostgreSQL | Состояние контейнера, порт и совпадение учётных данных |
| Отсутствует SQL-функция | Применены ли миграции через `go run ./cmd/migrate up` |
| Тайм-аут словаря | Доступность сети и сервиса; повторить ввод слова |
| Тайм-аут отправки Telegram | Соединение с Telegram; состояние диалога и уже сохранённые данные |

Ошибки пишутся в стандартный журнал процесса. После неоднозначной доставки
сообщения можно заново открыть `/words` или `/sources`, чтобы проверить данные.
Перезапуск теряет незавершённые диалоги, но не записи PostgreSQL.
